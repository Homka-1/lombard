## Принятые решения
- **Проценты** — простые, за каждый начатый локальный день с выдачи или последнего
  продления, минимум один день за период; после срока начисляются по той же ставке (без
  штрафов). **Срок** — до 23:59:59 последнего дня по времени Казахстана.
- **Продление**: новый срок отсчитывается от дня продления (клиент выбирает срок в пределах
  категории, по умолчанию — прежний); сумма займа не меняется.
- **Выдача** — по запросу клиента с номером карты: переходы `FUNDS_ISSUED`/`LOAN_ACTIVE`
  делает система (так требует машина состояний), в истории видно, на какую карту ушли
  деньги. Неудачный перевод ничего не сохраняет (займа ещё нет), неудачное списание —
  сохраняется как `FAILED`.
- **Погашение — только полное**: частичных платежей нет (как в типичном ломбарде).
- **Возврат изделия** оформляется на статусе `REPAID` (новых статусов не нужно): запись
  в таймлайне + задача `RETURN`, курьерский `deliver` → `ITEM_RETURNED`.
- **Номера карт не хранятся**: в платеже только маска и ссылка провайдера.
- **Часы** — смещение в памяти процесса (а не в БД): проще и не может «застрять» в проде;
  перемотка только вперёд, `run_jobs` по умолчанию сразу обрабатывает просрочки.
- **Залоговый билет** — HTML без внешних библиотек (PDF-генератор не добавлялся); ссылка
  требует Bearer-токена — фронтенд скачивает его через `fetch` → blob.

## Известные проблемы и техдолг
- Перемотка времени не влияет на `created_at` моделей, создаваемых без явного времени
  (заявки, фото, оценки, оферты, задачи курьера); статусы, платежи и уведомления этапа 8
  пишутся по часам приложения. Порядок таймлайна — по `id`, поэтому не ломается.
- Фоновой задачи-планировщика нет: обработка — при чтении займа и через
  `POST /api/admin/jobs/run` / `POST /api/admin/clock`. Для прода — cron/APScheduler.
- Нет напоминаний «скоро срок» (SMS за N дней) — нужна дедупликация отправок.
- Перенос/отмена возврата изделия не реализованы (только первичная запись).
- Нет отмены вызова курьера, пути «изделие не прошло осмотр» и отказа клиента от
  уменьшенной на осмотре суммы (долг этапа 7).
- Конкурентные платежи по одному займу не защищены блокировкой (SQLite, учебный проект).
- После `FORFEITED` нет учёта реализации изделия (продажа, остаток клиенту).
