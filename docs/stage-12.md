## Что сделано
- **E2E (Playwright 1.63, `frontend/e2e/`, `npm run e2e` / `make e2e`):**
  - `serve-backend.mjs` — поднимает backend на чистой SQLite (`backend/.e2e/`):
    `alembic upgrade head` → `app.seed` → `uvicorn :8001`; `playwright.config.ts`
    дополнительно поднимает Vite на `:5174` с прокси на этот backend. Режим
    `E2E_BASE_URL=…` — прогон против уже запущенного стенда (например, Docker).
  - `smoke.e2e.ts` — полный путь одной заявки в 4 браузерных сессиях: регистрация клиента →
    мастер (категория, параметры, 3 фото, проверка качества) → предоценка → эксперт:
    очередь, взятие, зум фото, предложение с комментарием → клиент: принятие, вызов курьера
    (первый свободный слот) → курьер на 375 px: три шага → эксперт: осмотр → клиент: отказ
    банка (ошибка поля) и выплата → продление на 7 дней → админ: +7 и +1 день, просрочка
    на дашборде → клиент видит «Просрочка» и гасит → админ возвращает реальное время →
    возврат изделия курьером → «Изделие возвращено» и заявка в «Завершённых».
    На 11 шагах — аудит axe-core; в конце — нет ошибок консоли и 5xx API ни у одной роли.
  - `a11y.e2e.ts` — все разделы всех ролей + первая карточка каждого списка: axe
    (WCAG 2.0/2.1 A и AA) на 1280 и 360 px, нет горизонтальной прокрутки на 360 px.

## Принятые решения
- E2E поднимает собственный backend на отдельной БД и порту (8001/5174), чтобы не задевать
  dev-базу и чтобы прогон был детерминирован; часы сбрасываются через API в начале теста.
- `reducedMotion: "reduce"` в e2e: тосты анимируются через `prefers-reduced-motion`, и axe
  иначе замерял контраст в середине fade-in (ложное нарушение).
- `audit()` ждёт стабильного состояния (нет запросов, `aria-busy`, «Загрузка»), чтобы не
  ловить промежуточные кадры.
- `playwright-core` закреплён на 1.63.0 через `overrides` — `@axe-core/playwright` иначе
  тянет более новую версию с несовместимыми типами и без скачанного браузера.
- Контраст исправлен в токенах, а не точечно в CSS: тот же цвет используется бейджами
  статусов во всех кабинетах и в макете.
- Docker-окружение по умолчанию — `development` (учебное демо с перемоткой времени);
  для внешнего размещения — `LOMBARD_ENVIRONMENT=production` + свой ключ (README).

## Известные проблемы и техдолг
- E2E покрывает основной «счастливый» путь с просрочкой; ветки «Запросить фото», «Отклонить
  заявку», «Отказаться от предложения» и изъятие (`FORFEITED`) проверены unit- и
  backend-тестами, но не в браузере.
- `npm audit`: 12 находок (2 critical, 10 moderate). Critical — `vitest`/`tinypool`
  (только тестовый раннер, локально), moderate — `typescript-eslint`/`minimatch` (линтер) и
  `react-router` 6 (open redirect через `/\` в `<Link>`/`navigate`, SSR-гидратация).
  Для приложения неэксплуатируемо: SSR нет, единственный путь «извне» — `from` после входа,
  он берётся из состояния роутера и обязан начинаться с `/<роль>/` (`canVisit`). Исправления
  — только мажорные обновления (vitest 5, react-router 7), отложены как отдельная задача.
- Остальное из `stage-11.md` в силе: опрос вместо WebSocket, у админа нет экрана заявки,
  нет сброса пароля сотрудника, перемотка времени глобальная.
- PostgreSQL в docker-compose не добавлен (SQLite в томе); для PostgreSQL нужен `psycopg`
  и `LOMBARD_DATABASE_URL`.
